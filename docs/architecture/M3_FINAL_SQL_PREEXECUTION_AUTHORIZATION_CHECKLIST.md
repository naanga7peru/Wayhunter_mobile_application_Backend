## Revocation bootstrap and dependency order

All eight REV tests invoke `M3MembershipRevocationSqlConcurrencyTests.EnsureSchemaAsync` directly or via seed setup, including Invitation Decision, Rollback and SQL Execution Strategy. The first caller in a given test process can invoke shared-context EnsureCreated. No fixture-order dependency exists inside that process. The helper serializes setup with a static semaphore and sets its flag after successful return. It does not coordinate processes, verify an existing catalog's schema, or guarantee renewal after external catalog changes. Failed bootstrap leaves the flag unset; hold retries until the coordinator determines catalog state. Do not use a test case as an implicit provisioning contract.

Future sequence requiring approval: obtain exclusive runner reservation and positively verify the exact target; approve either fresh shared-model provisioning via the helper or separately verified existing disposable schema; run the approved class/instance filter under a single process; verify outcomes and fixture-keyed cleanup. Serialize independent runs, while preserving intra-test competing contexts. Invitation requires Users, Trips, TripInvitations and TripMembers with the open-recipient, unique invitation/member constraints and required FKs. Revocation also needs the member outbox, its member FK, one-event uniqueness, pending lookup and state checks. Shared-context EnsureCreated may provision all mapped tables, including unrelated modules. It is never an upgrade or a migration check. Fixed-catalog teardown deletes only fixture-keyed rows and retains the catalog.

## Safe Check-in create/drop gate

The fixture validates the template and local server first, constructs a per-test GUID name and stores that exact connection privately for create, writes and teardown. It never enumerates or drops catalogs by prefix. Teardown uses the same reduced-schema options and calls EnsureDeleted only if its in-memory flag was set. Setup failure invokes disposal. If the process is killed or creation completes ambiguously before the flag is assigned, disposal cannot establish cleanup.

**Ownership blocker:** a true EnsureCreated result can also mean tables were created in an existing empty database. The current flag therefore does not prove the fixture created the catalog. GUID collision avoidance narrows risk. It does not enforce exclusive ownership of a pre-existing empty catalog. Before enabling automated drop, require a separately reviewed creation operation that fails if the exact catalog exists, records its exact identity and successful ownership, and revalidates ownership before drop. For interrupted runs, use a durable run record with revision, exact catalog, owner, start time, creation confirmation and outcome. An exact name or prefix match alone never authorizes deletion. No fixture source changes were made.

- **Assertion failure or failed rollback:** stop scheduling work and retain the failing test, exact target, transaction outcome and bounded logs. Under approved read scope, compare committed rows from a separate context and record divergence. Resume only after the coordinator accepts the diagnosis and rerun scope.
- **Interruption, termination, failed cleanup or orphan:** record last known checkpoint and exact target. Verify runner termination and transaction state under approved read scope. Quarantine ambiguous targets and escalate. Require written per-catalog or per-key cleanup authorization and positive ownership evidence before any cleanup.
- **Competing runner, lock or identity mismatch:** halt before new work. Confirm owner, lease and exact instance/catalog under approved read scope. Leave the target untouched until the coordinator resolves ownership or contention. Recovery never relies on a name prefix, clears another runner's data, or reuses an unverified catalog.
