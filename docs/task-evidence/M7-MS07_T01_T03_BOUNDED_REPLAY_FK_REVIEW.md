### Failure sequence and allocator limitation

At T0 the issuer creates credential R1. At T0+2m R1 is accepted and its SQL transaction commits. A backup from before that commit is restored. At T0+3m, while R1 remains inside its original `[T0,T0+10m)` first-acceptance interval, the unchanged valid credential is resubmitted and the restored database has no receipt. A globally unique allocator does not prevent a duplicate here. It prevents a future mint from reusing R1, but it does not prove that the absent receipt was never committed before a restore erased it. The restored database therefore cannot distinguish never-accepted R1 from previously accepted R1 using its own rows.

### Required safety invariants and blockers

1. A missing receipt after restore is **unknown**, never proof of non-acceptance. Do not run the fresh-acceptance path for an affected credential domain until reconciliation or fencing proves it safe.
2. Any credential that could have produced a commit lost by restore is either reconstructed as accepted or permanently fenced from new acceptance. Do not reissue R1 with a new DeliveryId, rotated signing key, refreshed session or later deadline.
3. Fencing and recovery state must be monotonic across replicas, failover, allocator leases, managed-key rotation/retirement, backups, restore, and disaster recovery. Compromised or retired signers cannot mint or validate around the fence.
4. Legacy, internal, fallback and recovery routes enforce the same gate. Disable legacy caller-generated keys before any future activation.
5. Resolve in-flight and ambiguous commits against authoritative durable evidence before reopening. A lost HTTP acknowledgement does not make an accepted operation absent.
6. Reconcile quota projections and reporting checkpoints. Any unrecoverable gap remains marked incomplete; do not report verified zero.
7. If any proof is missing, affected issuance and intake stay closed. Current design has no validated issuer or independent recovery authority, so restore safety remains **BLOCKED FOR DESIGN DECISION**. No SQL test or allocator uniqueness claim proves restore safety by itself.

### HTTP 409 reachability

Under the stated v1/v2 contract, all payload digest inputs are in the authenticated signed tuple: v1 binds AdvertisementId, EventType and RetryEventId; v2 adds the approved DeliveryId. The server validates this exact tuple before receipt lookup, and the receipt pins the same version and digest. Altering any signed input fails credential validation before lookup. For a matching valid tuple, the payload digest is deterministic and matches the pinned value. Therefore an authorized owner cannot currently present an otherwise-valid signed v1/v2 credential with a different payload digest. A changed DeliveryId is a signed-tuple mismatch, not a post-validation 409.

HTTP 409 is **UNREACHABLE under these assumptions** and remains reserved for a future approved contract or a separately demonstrated reachable conflict. Do not add an unsigned payload field to manufacture reachability. M1/M7 must review any future contract that changes the signed inputs, versioning or conflict semantics.
