# M1-M7 Administrator Role Storage Schema Proposal

**Project:** WAYHUNTER Backend
**Owner:** M1 IdentitySocial
**Consumer:** M7 HomeAdsAnalytics
**Status:** PROPOSED - Final DB approval pending
**Scope:** Schema design documentation only

## 1. Purpose

Define an authoritative server-controlled source for
Administrator role assignments.

Kaviyan approved the M1-M7 role claim contract and
Phase A implementation.

The storage approach was approved in principle only.

This document does not authorize SQL migrations,
schema changes, role grants or production activation.

## 2. Approved Security Contract

- M1 owns trusted Administrator role resolution.
- Approved claim type: ClaimTypes.Role
- Approved role value: Admin
- Role assignment must come from a trusted
  server-controlled source.
- Only an active, verified M1 account with a
  valid, non-revoked session may qualify.
- Missing, invalid, inactive, revoked or unavailable
  role assignments must fail closed.
- Client-supplied role claims are never authoritative.
- M7 owns centralized Admin endpoint policy integration.

## 3. Proposed Table

Table name: UserRoleAssignments

Proposed columns:

| Column | Type | Requirement |
|---|---|---|
| AssignmentId | uniqueidentifier | Primary key |
| UserId | nvarchar(256) | Required; M1 Users.UserId |
| Role | nvarchar(64) | Required |
| Status | nvarchar(16) | Required |
| AssignedAtUtc | datetimeoffset | Required |
| AssignedByUserId | nvarchar(256) | Optional for approved system bootstrap |
| RevokedAtUtc | datetimeoffset | Nullable |
| RevokedByUserId | nvarchar(256) | Nullable |

All types and constraints require final DB review.

AssignmentId must be generated by a trusted server
component, never accepted as proof of authorization.

UserId and actor IDs use M1 GUID-formatted string
identity semantics.

## 4. Proposed Foreign Keys

Primary relationship:

UserRoleAssignments.UserId
    -> Users.UserId

Proposed constraint:

FK_UserRoleAssignments_Users_UserId

Proposed deletion behavior: NoAction

The UserId SQL type, length and collation must
match the approved M1 Users schema.

Additional proposed audit relationships:

AssignedByUserId -> Users.UserId
RevokedByUserId  -> Users.UserId

Audit foreign keys and system-assignment handling
require separate DB Coordinator decisions.

Deleting an M1 user must not silently destroy
Administrator assignment audit history.

## 5. Role and Status Contract

Approved Administrator role value:

Admin

Proposed storage status values:

- Active
- Revoked
- Inactive

Authorization requires exactly:

Role = Admin
Status = Active

Role and status comparisons must be deterministic.

Other or unknown values must never grant access.

Future role types require separate approval.

## 6. Assignment Timestamps and Audit

AssignedAtUtc records the approved assignment time.

AssignedByUserId identifies the trusted actor that
created the assignment.

RevokedAtUtc records the effective revocation time.

RevokedByUserId identifies the trusted revoking actor.

Proposed consistency rules:

- AssignedAtUtc is required.
- Active assignment must not have revocation metadata.
- Revoked assignment requires RevokedAtUtc.
- RevokedAtUtc must not precede AssignedAtUtc.
- Inactive status semantics require final approval.
- System bootstrap assignments must have a documented
  approval and audit process.

The coordinator must approve whether actor IDs are
mandatory, nullable, or represented by a separate
system actor model.

No public API may directly assign Administrator roles.

## 7. Duplicate Active Assignment Prevention

Proposed database index:

Unique filtered index on (UserId, Role)
WHERE Status = 'Active'

Purpose:

Prevent more than one active assignment for
the same user and role.

Historical revoked assignments may remain stored.

The role reader must reject ambiguous or
inconsistent assignment data.

Do not silently select an arbitrary row when
multiple active assignments exist.

The DB Coordinator must approve filtered-index
syntax and compatibility with the final schema.

## 8. Proposed Indexes and Constraints

Candidate indexes:

- PK_UserRoleAssignments
- UX_UserRoleAssignments_Active_UserId_Role
- IX_UserRoleAssignments_UserId_Status
- IX_UserRoleAssignments_AssignedAtUtc

Candidate constraints:

- Non-empty UserId
- Non-empty Role
- Allowed role value(s)
- Allowed assignment status values
- Valid revocation timestamp ordering
- Consistent revocation fields

The final design must avoid redundant indexes
and must be verified against actual SQL query plans.

No constraint is approved for migration by
this document alone.

## 9. Runtime Administrator Resolution

Proposed request flow:

1. Validate M1 JWT signature and lifetime.
2. Resolve authenticated M1 UserId.
3. Verify persisted account is Active and Verified.
4. Reject deletion-requested accounts.
5. Verify persisted session ownership and validity.
6. Reject revoked or expired sessions.
7. Read Administrator assignment from the approved
   server-controlled source.
8. Validate assignment UserId, Role and Status.
9. Reject missing, invalid or ambiguous assignments.
10. Return ClaimTypes.Role = Admin only when eligible.
11. M7 evaluates the approved Administrator policy.

Administrator eligibility must reflect current
server-side state during authenticated requests.

JWT role claims supplied by clients must not
override stored assignments.

## 10. Role Storage Unavailable

If role storage cannot be accessed:

- No Administrator privilege is granted.
- No fallback to a client-supplied role.
- No fallback to an unapproved configuration grant.
- No assumption that an old assignment remains valid.
- The failure should be observable through safe
  server-side logging and monitoring.

Cancellation must be respected.

Operational error-handling and service availability
behavior require final implementation review.
